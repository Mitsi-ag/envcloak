# EnvCloak: running a command with secrets

Status: M1, and from M2 `--wait` and `--manifest` (task M2-03). This file fixes how SPEC §6.1 steps 5 to 9 are carried out: how the daemon releases a covered run's values, what the CLI does with them, how the command's output is redacted, and how signals, exit codes and a command's descendants are handled. The code is in `crates/envcloak-exec` (the runner), `crates/envcloak-cli/src/cmd/run.rs` (the command) and `crates/envcloak-daemon/src/requests.rs` and `state.rs` (the release). How a request is decided is in docs/GRANTS.md; the wire form of `run.request` is in docs/IPC.md.

## Finding the manifest and waiting

- **The manifest.** `envcloak run` finds the nearest `envcloak.toml` upward from its working directory, or takes the absolute path `--manifest` names (a relative one is a usage error, exit 2, and is not echoed). Either way it sends the path and the daemon opens it itself, with every rule of SPEC §6.1 step 2 and docs/MANIFEST.md: the file must be named `envcloak.toml` (`invalid_path`), not be a symlink (`symlinked_manifest`), be a regular file of this user, and the project is the canonical directory with its device and inode. So a directory named through `--manifest`, from any working directory or through a symlinked directory, is the same project as when the manifest is found upward, and a grant for one covers the other. Adoption (SPEC §6.4) is unchanged.
- **Waiting.** Without `--wait`, a request no grant covers exits 125 with `approval_required request=<id>`. With `--wait <duration>` (`<n>s` or `<n>m`, 1 second to 10 minutes, the pending request's lifetime), the run prints that line once, with how long it waits, and waits for the approval without holding a connection: it polls the request's state (`pending.state`) on fresh connections, pausing 250 ms for the first second, 500 ms for the next, then 1 second, and longer, doubling up to 2 seconds, when the daemon answers `busy`; it never treats `busy` as a refusal. Approved, it asks `run.request` again and runs as a covered run does. An approval it reads only after its deadline (a poll the daemon answered during the grace), and, once a request was named, a covered answer it reads after the deadline that does not follow an approval read in time, may come from an approval given after the deadline: the run then exits 125 as at the deadline, and starts nothing (the grace finishes a run approved within the wait, never one approved during it). Denied, it exits 125 with `approval_denied`. Still pending at its deadline (polled once more there), or expired, it exits 125, its `approval_required` line being the failure. A request over a pending cap (`too_many_pending`: the root has 3 waiting, or the daemon 20) prints that line once and is asked again with the busy backoff until a place frees or the wait ends (then exit 125). `unknown` at or after the deadline is not asked again. A call the daemon did not take (its connection closed unanswered, as the daemon closes one when 32 are open; or, once the daemon has answered this wait, nothing listening there) is asked again with the busy backoff until the deadline, where it is the failure (`daemon_unavailable`); before any answer, no daemon there is said at once, as without `--wait`. The wait never outlasts its deadline by more than 5 seconds, or by the shorter grace `--wait-grace <n>s` gives (1 to 5 seconds; `envcloak mcp` passes 1, so that its tool answers within its host's timeout, docs/MCP.md). A waiting run makes no connection outside its wait: its first contact with the daemon is the wait's first `run.request`. Every call of the wait is bounded by that one limit from its connect to the last byte of its answer: the connect is given the time left (a listener whose backlog is full holds it no longer on Linux, and macOS refuses it at once), and before each write and each read the run waits for the socket only for the time then left, so a daemon that answers nothing, sends its answer a byte at a time, or reads the request slowly holds it no longer (tests: `crates/envcloak-ipc/tests/wait.rs` and `crates/envcloak-cli/tests/wait.rs`, `a_wait_on_*` and `a_daemon_*`). An answer read after the limit is dropped, a covered one's values wiped with it; the run then exits 125 with `daemon_unavailable`, saying the daemon did not answer within the wait, and starts nothing. Before each `run.request` while it waits, whose answer may carry values, the run looks again for a tracer attached to it (the check of gate 19, made once before the first request, would otherwise be minutes old) and exits 125 with `traced` without asking if one is. It reads no terminal and no input while it waits (gate 23): approval comes only from `envcloak approve` in a terminal of the person's own, and `envcloak pending` there finds the request's id. SIGINT and SIGTERM end the wait as they end any program, also when the run was started with them ignored (as a shell starts a background job with SIGINT) or blocked (a program that takes these signals on one thread blocks them in every thread, and a child inherits that mask unless it is started without it, as `envcloak mcp` starts its children), both of which survive `exec`: before the wait the run gives SIGINT and SIGTERM their default action and unblocks them and SIGHUP, so the run holds nothing open then, a shell reports 130 or 143, and no approval that comes later starts the command; one sent before the wait began, while it was blocked, ends the run there. SIGHUP keeps the disposition the run came with, so a run started under `nohup` still ignores a hangup. Docs: GRANTS.md "Waiting and finding a request".

## Release

A covered `run.request` is a delivery. The daemon, holding its state lock since the decision:

1. refuses (`traced`) while a tracer is attached to it;
2. reads each binding's value from the verified vault. A read that meets a row changed on disk while the vault is open turns the vault tampered (T3), and the request fails with `vault_tampered`: nothing is released, then or later, from that vault;
3. builds the answer and frames it as it will be sent, in a buffer wiped on drop: for each binding, in the order the daemon resolved them, the variable, the item's slug, its `allow_short`, and the value as base64 in a wiped buffer. An answer larger than one frame (1 MiB) is refused here, `frame_too_large` (F-77), before anything is committed: no value is released, no delivery is recorded (the refusal is, as `request decision=frame_too_large` with its grant), and the grant is left as it was, so a `once` grant still covers a request for fewer or smaller values;
4. asks again whether the grant is in force, on clocks read now: the reads and the framing come after the decision, and a grant that ran out meanwhile (its wall-clock or awake-time deadline passed), or whose root process exited meanwhile (a grant never outlives its root, SPEC §10b; the state lock the daemon holds keeps the tick's sweep from removing it), commits nothing. The answer is dropped (and wiped), nothing is recorded or released, a grant whose root exited is removed, and the request is decided again on those clocks, as one arriving now would be: the grant covers nothing, so it is pending, or covered by another grant still in force;
5. writes the delivery's audit entry and flushes it to disk (`State::deliver`). When it cannot, the request is denied with `audit_failed`, the answer is dropped (and wiped), and a `once` grant stays unused;
6. only then uses a `once` grant and sends the answer. A failure while the answer is written is not undone: some of it may have reached the client.

A pending or denied answer carries no value. The client refuses an answer with values beside another decision, a variable or slug of the wrong shape, a variable named twice, or an empty value or one holding a NUL byte (`protocol_error`): a program running as the user can answer in the daemon's place (SPEC §1.1).

## The command

`envcloak run` closes its connection to the daemon, then:

1. **Short values** (gate 9). A value under 8 bytes is never injected. A value of 8 to 15 bytes is injected only when its item has `allow_short` (`envcloak add --allow-short`). Otherwise the run exits 125 with `value_too_short`, naming the items by slug, and starts nothing. The limits come from the redactor: a shorter value would match ordinary output.
2. **The redactor.** One redactor for the run, labeled with the items' slugs: a value is replaced by `[envcloak:<slug>]`, and so is each encoding `envcloak-redact` covers (the value raw; base64 and base64url, padded and unpadded, whole or inside a longer base64 stream; lower and upper hex; percent-encodings of common encoders; JSON escapes of common serializers). What it covers less than fully is printed on standard error before the command starts, one line per item: `envcloak: coverage: <slug> is 8 to 15 bytes (allowed short)`, `envcloak: coverage: <slug>: inside a longer base64 stream it is redacted at some byte alignments only` (too few whole base64 groups at some alignment), and `envcloak: coverage: <slug>: JSON escapes are redacted as common serializers write them, not in every combination of options`.
3. **The environment** (gates 13 and 14). The command gets this process's environment plus the env file's ordinary variables and the bindings' values. The values are set only in the new process's environment: never in argv, a temporary file or the CLI's own environment. `Command::env` copies them into strings that are freed right after the spawn; the wiping allocator clears those, as it clears the copies the redactor's automata keep (gate 11). The CLI keeps the redactor, and nothing else holding a value, until the command ends.
4. **Output.** Standard output and standard error are separate pipes, each read by its own thread through its own stream of the redactor: `push` on every read, `flush_idle` after 40 ms without output (so a prompt without a newline shows at once, unless it could be the start of a value), `finish` at end of stream. Only what the redactor releases is written. Relative order between the two streams is not kept. Standard input is inherited.
5. **No terminal.** The command's standard output and standard error are pipes, not a terminal, so a program that colors its output or pages only on a terminal prints plain text. There is no switch to unredacted passthrough when a terminal is present. PTY mode (`--pty`, merged output through the redactor) is M2's (what is built for it so far: "PTY mode: what M2-17 builds" below); until it lands, `--pty` exits 125 with `not_in_this_build` before anything is sent.

## Signals and exit

- **With a controlling terminal** the command stays in the CLI's process group. The terminal sends SIGINT (Ctrl-C) and SIGQUIT (Ctrl-\\) to both; the CLI catches them and stays, so what the command prints on its way out is redacted too, and does not pass them on (the command has them already). SIGTERM and SIGHUP, which are sent to the CLI alone, are passed on to the command, and so are a SIGINT or SIGQUIT that another process sent the CLI by its pid (`kill -INT`, `timeout --foreground -s INT`, a harness's `send_signal`): the terminal did not send those to the command.
- **Who sent a signal.** The CLI catches with `SA_SIGINFO` and reads the sender from the kernel. On Linux, `si_code` says it exactly: `SI_USER`, `SI_QUEUE` or `SI_TKILL` for a process, `SI_KERNEL` for the terminal. macOS reports a terminal's Ctrl-C exactly as a `kill` from the process that wrote the keystroke to the terminal (`si_code` 0; the terminal emulator's, `sshd`'s or `tmux`'s pid), and that process holds the terminal open and is outside the session it controls. So on macOS a signal counts as sent by a process when its sender is in the CLI's session (a parent such as `timeout --foreground`, a harness started from the same terminal, the command itself) or is already gone (`kill(1)`, which exits once it has sent). A SIGINT or SIGQUIT from a live process in another session (`kill -INT` typed in another terminal's shell) cannot be told from the terminal's there, and is not passed on: send SIGTERM, or signal the command itself. A process that signals the CLI's whole process group (`kill -INT %1`) reaches the command directly and through the CLI, so the command gets that signal twice, as it does SIGTERM and SIGHUP.
- **Without one** (an agent's tool call, a service), the command leads a process group of its own, and the CLI passes SIGINT, SIGTERM, SIGHUP and SIGQUIT on to that group.
- **A second SIGTERM** ends the command at once. The first SIGTERM the CLI gets while the command runs is passed on as it is; from the second on, the CLI sends SIGKILL in its place, to the command's group without a terminal and to the command on one. A command that ignores SIGTERM would otherwise outlive the CLI when it is killed in turn, still holding the values, in a group nothing else owns. `envcloak mcp` relies on it to end a cancelled call's command (docs/MCP.md "Cancellation"): it sends `envcloak run` SIGTERM, a second SIGTERM 2 seconds later, then SIGKILL.
- **What a SIGTERM leaves behind.** Without a terminal, once the CLI has passed a SIGTERM on, what is left of the command's group when the command exits is killed: the CLI sees the exit without reaping the command (`waitid(WNOWAIT)`), sends the group SIGKILL while it is still the exited command's own, and reaps the command only after its output has been read. So a command that dies of the SIGTERM but leaves a descendant in its group that ignores it, with or without the output pipes, does not leave that descendant running with the values. A SIGTERM that reaches the CLI only after the command exited, while its output is still read (a descendant holding the pipes, up to the 2-second cutoff below), stops the run (below) and kills what the command left in its group the same way, before the reap: the CLI stops passing signals on, reads every signal caught until then, and only then decides. A command that ends by itself, its output read, and no SIGTERM before that, leaves what it started running. With a terminal the command shares the CLI's group, which the CLI does not signal; `envcloak mcp`, which starts each `envcloak run` in a group of its own, kills that group instead (docs/MCP.md "Cancellation"). A process the command started in a group or session of its own is outside either group.
- The four signals are caught, never ignored, from before the command starts until it ends; `exec` resets a caught signal to its default, so the command starts with the usual dispositions. A blocked signal is never caught, and a signal mask survives `exec`, so a program can start the CLI with some of them blocked: the CLI unblocks the four on the thread that catches them (the threads it starts afterwards inherit that), and blocks again after the run those that were blocked. The command starts with no signal blocked. A signal is passed on only while the command has not exited: the CLI sees the exit with `waitid(WNOWAIT)` and stops passing signals on before it reaps the command, so its pid, and the group it leads, cannot belong to another process by then; and before it passes a signal on it asks the kernel whether the command has exited already (`waitid` with `WNOHANG` and `WNOWAIT`), so a signal that comes after the exit, before the CLI has seen it, is handled as one read after the exit (below), never passed to what the command left in its group.
- **A signal after the exit.** The CLI marks, among the signals it has caught, the moment it sees the command's exit. A SIGINT, SIGTERM, SIGHUP or SIGQUIT caught after the mark has no command to go to, and stops the run at once: the pipes are closed, what was still to be read or written is dropped (never passed through), and the CLI exits with 128 plus the signal's number, as the signal asks. A signal caught just before the mark but read once the command has exited, which would have been passed on, has no command to go to either, and stops the run the same way (a terminal's own SIGINT or SIGQUIT, which reached the command too, is left alone); and when the mark cannot be written (a flood of signals not read yet fills the pipe that carries them), every signal read from then on stops the run. A signal that finds that pipe full is not lost: the CLI keeps one of each signal and sender aside, without blocking or allocating in its handler, and handles it like one read from the pipe, on its side of the mark (a SIGTERM behind thousands of SIGINTs still reaches the command, or stops the run after the exit). Only a signal already kept aside and not handled yet is merged with its repeat, as the kernel merges a standard signal sent twice before it is caught. So a run whose output waits for a reader, or for the cutoff below, can always be ended without SIGKILL, and the redactor's copies of the values go with it.
- **Exit.** The CLI exits with the command's code, or 128 plus the number of the signal that ended it or stopped the run after it. A command that does not exist exits 127 (`command_not_found`), and one that cannot be run 126 (`command_not_executable`), as with `env(1)`. EnvCloak's own failures exit 125 with one token. The CLI's own: `approval_required`, `approval_denied`, `value_too_short`, `traced`, `protocol_error`, `daemon_unavailable`, `daemon_unverified`, `usage` (no command after `--`) and `run_failed`, and `manifest_invalid` and `binding_unresolved` for a manifest or `--env-file` it refuses before asking. Any other is the kind of the daemon's refusal (docs/IPC.md "Error tokens"), as is, among them `vault_locked`, `vault_tampered`, `too_many_pending`, `manifest_invalid`, `binding_unresolved`, `policy_denied` (the effective policy refuses the agent), `mode_unsupported` (the effective mode is proxy), `evidence` (the caller's ancestry could not be read), `login_reference` (a binding names a login's field, which is never bound, SPEC §6.8) and `frame_too_large` (the answer the values make is larger than one frame, F-77; nothing was released and the grant is as it was). The list is not closed: a run prints whatever kind the daemon refused it with. The command is never `exec`ed in the CLI's place: that would end redaction.
- **Descendants.** After the command exits, output is read until end of stream. A pipe that a descendant still holds 2 seconds later is cut off: the CLI closes it, gives up any write to its own output still waiting then (so a reader that has stopped reading cannot keep the descendant's pipe open), releases what was held back redacted as far as the output takes it at once, and what the descendant writes afterwards is lost (its next write fails), never passed through. A pipe that no process holds any more (the command and every descendant have closed it) is read to its end and delivered as fast as the reader takes it, as from any program, unless a signal stops the run.
- **A lost reader.** When the CLI's standard output (or standard error) can no longer be written, `EPIPE` for a reader that went away, the CLI closes its end of the command's pipe for that stream, so the command's next write fails with `SIGPIPE` or `EPIPE`, as it would writing to the reader directly (`envcloak run -- make | head`). The other stream goes on.
- **Backpressure.** A slow reader slows the command: nothing is buffered beyond one read (64 KiB) and what the redactor holds back. While the command runs, a write to the CLI's output waits for the reader as long as it takes. A write the CLI must give up (at the cutoff, or when a signal stops the run) is broken off by interrupting the thread blocked in it: the CLI catches SIGURG, with a handler that does nothing and without `SA_RESTART`, for the run, and sends it to its own output threads (`pthread_kill`) until they have given up; the command starts with SIGURG's default. Each output thread unblocks SIGURG while it runs, so a CLI started with it blocked still gives the write up.

## PTY mode: what M2-17 builds

`envcloak run --pty` lands with M2-19; until then the option exits 125 with `not_in_this_build`. M2-17 builds what it stands on: `envcloak_sys::pty`, `pty_monitor`, `owned` and `termios`, and `envcloak_exec::start_pty`. What follows is what the tests establish, on macOS 26.4 locally and on Linux (an Ubuntu 24.04 container on kernel 6.12 locally, and CI).

- **The command never leads its own session.** A command that leads a new session, with its parent outside it, is an orphaned process group: the suspend character typed on its terminal sends it SIGTSTP, and it does not stop. `crates/envcloak-sys/tests/pty_topology.rs` keeps that counterexample as a test (with SIGSTOP, SIGCONT and the interrupt character working, so it is job control that fails, not the relay). `start_pty` forks a **PTY monitor** that leads a new session on the PTY's slave side and starts the command as the slave's foreground process group, in a group of its own; its parent, the monitor, is in the same session, so the suspend character stops it. On a stop the monitor takes the terminal back and reports `Stopped`; on `Resume` it gives the terminal back first and only then sends SIGCONT, so a command continued inside a read of its terminal does not stop again on SIGTTIN. The suspend character stops `/bin/cat` and a cat that reads again on `EINTR`, on both systems, `Resume` continues them, and a job-control shell on an outer terminal regains its prompt when the suspend character stops a command run this way, with `stty -g` as before, `jobs` showing it stopped, and `fg` resumes it (the minimal form of M2-19's gate).
- **`/bin/cat` after a stop, measured:** stopped inside a read of its terminal and continued, macOS's `/bin/cat` gets `EINTR` from that read and exits 1 ("Interrupted system call"), under a plain job-control shell as under the monitor (BSD cat does not read again after `EINTR`); Linux's reads on. So the tests hold `/bin/cat` under the monitor to what it did under a plain shell in the same run, on each system, and require the round trip after `Resume` and after `fg` from the cat that reads again on `EINTR`, on both systems. That is how the spike's kill criterion is judged: a missing stop or report, the outer prompt, `jobs`, `stty -g` or `fg` failing, `/bin/cat` doing other than its baseline, or the retrying cat's round trip failing, on either system, would cut job control there. None did. The order of `Resume` (the terminal handed back before SIGCONT) is gated every time, on both systems, by the monitor's model test; the real (b) and (c) cases catch SIGCONT sent first on macOS only some of the time (2 of 5 runs in a review) and not on Linux.
- **The monitor** holds the slave on descriptors 0 to 2 and its control channel to the CLI on 3, and nothing else; the command starts with the slave on 0 to 2 and nothing else. It closes every descriptor it inherited, also one opened before the CLI lowered its limit and now above it: on Linux `close_range`, or where that fails the `/proc/self/fd` listing until a pass finds nothing; on macOS the `proc_pidinfo` listing until a pass finds nothing; where no listing can be read it reports `SetupFailed` and starts nothing. It allocates nothing after the fork (a stop, resume and exit cycle runs under an allocator that aborts in any other process), observes the command's exit without reaping it and signals only its own unreaped command's group. Only an exit record counts as the command's exit: macOS's `waitid`, asked for exits only, also returns a stopped command's stop that nothing has consumed yet, which a monitor that took it for an exit reported as a death by SIGTSTP before it hung reaping a command that was only stopped; a command that stops itself again after each `Resume`, thousands of times, is reported stopped each time and exited only when it is killed. The M1 runner's exit observers (`has_exited`, `wait_for_exit`) read the record's kind the same way. Once the command has executed, the monitor wipes its copy of the strings prepared for the exec (the paths, argv and the environment with the values); the rest of its memory is the CLI's as it was at the fork. It ignores SIGTTOU, SIGTTIN, SIGTSTP and SIGPIPE, and catches SIGINT, SIGQUIT, SIGTERM and SIGHUP to pass each on to the command's group (they reach it when its own group holds the terminal, the command stopped, or as the session's leader at a hangup), so none of them ends it. It is a fork of the hardened CLI: on Linux the test reads its core-file limit (0) and finds its environment unreadable; on macOS `ps -E` shows the CLI's own environment for it, without the value, and the zero core limit it inherits by the fork is not read back. If the CLI's end of the channel closes while the command runs, it hangs the command up (SIGHUP, then SIGCONT). If the monitor dies, the CLI sees the end of the channel (`UnexpectedEof`) at once, and the kernel hangs the session up. At the command's exit it waits, up to 2 seconds, until the CLI has read what the command wrote before it closes the slave: on macOS that close discarded a line the CLI had not read yet (macOS's `/bin/cat`, stopped and continued, writes its last line and exits; read 1.2 seconds later, the line is there only with the wait). The CLI must therefore read the PTY while it waits for the monitor's reports (M2-19's relay does). Its control messages are registered in docs/IPC.md (`pty_monitor`), checked against the code by `scripts/check-reservations.py`.
- **Owned children.** The monitor's pid is the session's id and the CLI's signal target, and both hold only while the monitor is unreaped. A process whose SIGCHLD is set to be ignored or carries `SA_NOCLDWAIT` may have its children reaped by the kernel as they exit. Measured, with the three ways a process comes to that: Linux reaps on its own for `SA_NOCLDWAIT`, for SIGCHLD ignored in the process, and for one ignored by whatever started it, inherited across `exec`; macOS 26.4.1 for the first two and not the third (and reads an ignored SIGCHLD set in the process back with `SA_NOCLDWAIT` set). So before every fork of an owned child (the monitor, and the M1 runner's command) SIGCHLD gets its default back, without `SA_NOCLDWAIT`, or nothing starts; and a signal sent by number (macOS, and every group signal) first checks that this process still does not reap on its own and that the child is still its own unreaped one (`waitid` with `WNOWAIT`), refusing with `ECHILD` otherwise. A CLI started with each of the three still reaps its monitor, and the M1 runner still waits for its command, on both systems.
- **Forwarded signals reach the terminal's foreground job**, which is a nested shell's job when one runs (`crates/envcloak-sys/tests/pty_signals.rs`, with a nested `/bin/sh -i` running a counting job; each signal counted once by the job and never by the shell):

  | Signal | Linux | macOS |
  |---|---|---|
  | SIGINT, SIGQUIT | `TIOCSIG` on the PTY's master side | `TIOCSIG` |
  | SIGTERM, SIGHUP | `TIOCSIG` refuses them (`EINVAL`); the foreground group as one, through its leader's pidfd (`OwnedSession`) | `TIOCSIG` |

  On Linux, for SIGTERM and SIGHUP, a pidfd is opened on the process whose pid is the foreground group's number (`TIOCGPGRP`), and only then is that process's session read from `/proc` and checked to be the monitor's; the signal then goes through the pidfd to the group that process leads or led (`PIDFD_SIGNAL_PROCESS_GROUP`, Linux 6.9), which the kernel resolves by the group's identity and signals at the moment of delivery. A process enters a session only by being created in it and a group never spans two sessions, so at the binding every member of the group is in the monitor's session; a member other than the leader that left the job (`setsid`, or `setpgid` to another group) before the delivery gets nothing, which the tests show with a job whose members leave after it was bound and before the signal; and a number reused since it was read names no member of that group, so such a signal reaches no one and is reported as an error, never as forwarded. The leader is the exception: its pid is the group's identity, so a leader that leaves its group for another of the session and then the session itself (`setsid`, which the kernel allows once its old group is empty) between the binding and the delivery leads a new group under that identity in a new session, and the signal reaches it there, with any process it started since: the job's own leader and its descendants, never a process the job did not start, but outside the monitor's session by then (a model test in `owned.rs` shows it). Where the kernel has no such signal, or the job's group leader was reaped (a pipeline whose first command ended first), SIGTERM and SIGHUP are narrowed to the command's own group, through the monitor, and `forward_signal` says so (`Narrowed`): with a nested shell that is the shell, not the job (shown with a `true | ...` pipeline on Linux, and with the group signal refused as an older kernel refuses it, on the kernel CI runs). The group signal through a pidfd is Linux 6.9's: every kernel before it narrows SIGTERM and SIGHUP this way, among them Ubuntu 24.04's original 6.8, Debian 12's 6.1 and RHEL 9's 5.14, so a job under a nested shell never gets those two there; M2-19's `run --pty` help is to name them. A member of the job the CLI may not signal (one that changed to another user) gets nothing; as with `kill(2)` of a group, the delivery counts as made when another member received it. While the command is stopped the monitor holds the terminal, and the job is the command's own group: every forwarded signal goes there through the monitor (`CommandStopped`) and waits until the command continues; a `TIOCSIG` racing the stop reaches the monitor, which passes it on. Linux's `TIOCSIG` reports success for a foreground group that has just emptied (the kernel's `pty_signal` ignores what the delivery returned), which happens only once the job has ended. macOS's `TIOCSIG` discards input typed and not yet read (the terminal's queues are flushed unless `NOFLSH` is set); Linux's does not. EnvCloak never signals a process group number it read from the terminal.
- **The outer terminal** is put in raw mode by a `TerminalGuard` and its settings come back with `TCSAFLUSH`, so input typed and not read is discarded, after a normal exit (`TerminalGuard::release`, which says whether the restore worked), an error, SIGTERM, SIGHUP, a panic in a release build (the panic hook restores; no destructor runs there) and SIGTSTP (restored while stopped, raw again after SIGCONT). Each of these is checked with input left unread before the way out, on Linux and macOS, through the guard's own reading of the settings and through `stty -g`. The panic hook's restore may run on another thread while the guard is dropped, a new one registered, or the terminal switched to raw mode: the restore holds the registration while it runs, so the guard's descriptor is not closed under it and its saved settings are not rewritten; a switch to raw mode under way ends before it, and one asked for after it is refused, so the process never ends with its terminal raw. A new PTY starts with the outer terminal's settings (a remapped or a disabled suspend character carries over, compared through `stty -g`) and size, both sides close-on-exec from their creation (`posix_openpt` with `O_CLOEXEC`), and a size set on the master reaches the command with SIGWINCH (read inside the PTY with `stty size`). The control channel is close-on-exec from its creation on Linux; macOS's `socketpair` has no such flag, so there it is set just after, and the session must be started before any other thread of the CLI can start a program (M2-19 does).
- **The environment** (gate 14). The command's environment is the CLI's with the values on top: an injected name replaces an inherited one, and of two entries for a name the last wins, one entry in the command's `environ`, as `Command::env` gives. The value is in the command's environment, readable by a process of the same user, and nowhere else the tests look: not in its argv or the monitor's, not in the CLI's environment, not on the terminal (read to its end), not on the CLI's standard output or standard error, and not in a file: the CLI and the command run with a home, a `TMPDIR` and a working directory of their own under a private root, the `TMPDIR` is empty after the run and no file under the root holds the value, while a canary written there on purpose is found.
- **Redaction.** The slave's line discipline writes every LF as CR LF (`ONLCR`), so the redactor gains the CR LF form of each value holding LF (`RedactorBuilder::crlf_variants`). The oracle is the kernel: `crates/envcloak-redact/tests/crlf_kernel.rs` has a real terminal write eight shapes of value (an inner, a leading and a trailing LF, two in a row, a CR LF already there, CR LF and LF mixed, a NUL and a multi-byte character, and none) and redacts what it shows, whole and split at every byte with and without an idle flush; without the variant six of those forms pass through. `crates/envcloak-exec/tests/pty_spawn.rs` shows a value written through `start_pty` comes out in that form.

## Status descriptor

A program that starts `envcloak run` and must know how the run ended (`envcloak mcp`'s `run_with_secrets`, docs/MCP.md) cannot tell it from the exit code and the output: they are the command's own, and a command can exit 125 after printing `envcloak: approval_required: ...` (Codex F-113). It passes `--status-fd N`, the write end of a pipe of its own, which the run inherits as descriptor `N` (3 or more):

- **Taken first.** Before the run reads anything else, it sets the close-on-exec flag on `N`, and on every other descriptor it inherited above the standard streams (listed from `/dev/fd`), and writes its record through a copy of `N` it owns alone (`F_DUPFD_CLOEXEC`), so nothing else that may hold the number is closed with it. The command therefore inherits none of them: not the status descriptor, and not a descriptor its starter holds by mistake (on macOS a socket or pipe gets its close-on-exec flag only after it is made, so a program that makes them on several threads can leak one into a child it starts meanwhile). A descriptor `N` that is not open is a usage error (exit 2). When the inherited descriptors cannot all be listed (`/dev/fd` or one of its entries unreadable), the run refuses with `run_failed` before anything is started, recorded `not_started`: it never guesses at their numbers, which could miss one above a lowered `RLIMIT_NOFILE`. A run without `--status-fd` passes inherited descriptors on to its command, as `env(1)` does: a shell's `3<file`, or a `make` jobserver, reaches the command.
- **One record.** As it ends, the run writes one line of JSON there, with one write of at most 512 bytes, which a pipe takes whole (`envcloak_client::run_status`): `{"v":1,"state":"not_started","token":"<token>"}`, with `"request":"<id>"` for `approval_required`, when EnvCloak refused before the command was started (whatever the exit code: 125, 2 for a usage error found after the descriptor was taken, 127 or 126 for a command not found or not runnable); `{"v":1,"state":"ran","code":<n>}` (or `"signal"`, or `"stopped"` for a signal that stopped the run after the command exited) when the command was started and followed to its end; `{"v":1,"state":"unknown"}` when the runner failed after the command may have started (`run_failed`). It holds no value, no output and no free text.
- **Read as written.** The reader takes only the exact line the run writes, its fields in that order and without spaces, as a record. No record, a second one, one cut short or too long, one of another version, one with a field its state does not take, and one written any other way (other spacing, field order or case) are unknown: the command may have run. A run killed before it writes the record (a signal, a crash) leaves none. Random and damaged records test this against an oracle written apart from the reader (`crates/envcloak-client/tests/run_status_fuzz.rs`).

## What another process sees

SPEC §1.1 says it plainly: other programs running as you can read a running process's environment. The tests record it on both systems (`crates/envcloak-cli/tests/run.rs`):

| | The CLI (`envcloak run`) | The command |
|---|---|---|
| macOS, `ps -E` | the environment it was started with: no value | the values (for a binary that is not a platform binary; macOS hides a platform binary's environment) |
| Linux, `/proc/<pid>/environ` | unreadable: the CLI is non-dumpable | the values: `exec` makes the command dumpable again |

Neither command line holds a value (gate 13).
