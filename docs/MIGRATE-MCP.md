# EnvCloak: managed MCP servers

Status: M2. Task M2-27 lands the records, the registered launches, the daemon's launch check and the daemon-started runner; `envcloak migrate-mcp` itself, which writes them from a host's MCP config, is task M2-20, and `envcloak mcp-bridge`, which the host runs in the server's place, task M2-18. This file fixes what a managed server's record holds, what its launch receipt says, what the daemon checks before it releases a key and to whom it releases it, and what that costs. The code is in `crates/envcloak-policy/src/managed.rs` (declarations, classes, the launch environment, the update statement), `crates/envcloak-daemon/src/{managed,launch_check,spawn_envcloak}.rs`, `crates/envcloak-exec/src/launch.rs` (the runner), `crates/envcloak-sys/src/{launch,codesign,owned}.rs` and `crates/envcloak-ipc/src/control.rs`. The wire form is in docs/IPC.md, the grant rules in docs/GRANTS.md "Managed servers".

## The record

A managed server's record (docs/VAULT.md "Policy records", kind 3) names its managed project by identity (canonical directory, device, inode) and how the server is reached:

- a **stdio server**: its registered launch: the absolute executable, resolved once, in the daemon, against the declared `PATH` (never at launch), with its identity read through a descriptor (Linux: SHA-256; macOS: the code directory hash, with the Team ID and signing identifier when signed) and device and inode; the whole argv; the working directory (the declared one, or the managed directory) by device and inode; the launch environment (the declared `PATH` and variables, and the names of the bindings); the class and the binding strength; a script's entry file by identity; and the declaration exactly as given, which an update starts from (CR-2);
- a **bridged HTTP server**: its exact origin and the header names its relay inserts. Every binding of its managed manifest carries the origin's digest in its name (`_O` and 16 hex digits of the origin's SHA-256), so an edited origin is a new binding, which asks for approval. Each header has exactly one binding, named by the header and the origin (`envcloak_policy::managed::bridge_binding_name`: the header's name upper-cased with each `-` written `_`, then the origin's suffix, so `Authorization` is `AUTHORIZATION_O<16 hex digits>`), and the manifest binds exactly those (registration refuses anything else, `invalid_params`, reason `header_bindings`; a header whose name is not made of letters, digits, `-` and `_`, or two headers that would share a binding, reason `invalid_header`). A request must resolve to exactly those bindings, and the relay's `Release` names each header with the binding whose value it carries, so the relay (task M2-18) inserts each value only in its registered header.

It also holds who registered it and the mark "written by migrate-mcp on this device". Only `managed.register`, with the passphrase, from a terminal subject, writes a record (the same rule as `approve`: no agent by any evidence, a terminal of its own, and no session or terminal shared with a waiting request of an agent or an unknown process, reason `requester_terminal`, checked again once the passphrase is verified; `managed.update_plan` answers such a caller nothing); a record of the same name or the same project is replaced, a stdio launch keeping its launch id with the next revision. The launch id and revision are taken from the record as it is when the registration commits, under the lock the commit holds, so a registration and an update that overlap never share a revision, and a name whose record was removed meanwhile gets a new launch id. `managed.unregister` removes one, with a proof (the same rule). A grant made while a project was managed is bound to its record (a stdio launch's revision, a bridged server's origin), so after a removal, a replacement by another transport or an update, none covers the project's requests; nor does a grant made while the project was not managed cover a managed request.

## Declarations EnvCloak refuses

A declaration whose environment sets a variable that selects code (SPEC §6.6: `LD_*`, `DYLD_*`, `NODE_OPTIONS`, `NODE_PATH`, `PYTHONPATH`, `PYTHONSTARTUP`, `PYTHONHOME`, `RUBYOPT`, `RUBYLIB`, `PERL5OPT`, `PERL5LIB`, `BASH_ENV`, `ENV` and the others of `envcloak_policy::managed::CODE_SELECTING`), or whose argv gives its interpreter an option that loads other code (`-e`, `-c`, `-m`, `-r`, `--require`, `--import`, `--loader`, node's `--inspect` forms and their kin), is refused `code_selecting_env` at registration (reasons `code_selecting_variable` and `interpreter_option`): what such a launch runs cannot be checked. Beyond SPEC §6.6's list, each interpreter EnvCloak classes has its own variables refused too: `PERLLIB`, `PERL5DB`, `PERLIO`, `JDK_JAVA_OPTIONS`, `CLASSPATH`, `PYTHONUSERBASE`, `PYTHONINSPECT`, `PYTHONBREAKPOINT`, `PYTHONPYCACHEPREFIX`, `PYTHONPLATLIBDIR`, `PYTHON_PRESITE`, `PYTHONWARNINGS`, `GEM_PATH`, `GEM_HOME`, `BUNDLE_GEMFILE`, `PHPRC`, `PHP_INI_SCAN_DIR`, `DENO_DIR`, `npm_config_*` variables except `registry`, `cache`, `fund`, `audit` and `update_notifier` (names compared case insensitively), `ZDOTDIR`, `XDG_CONFIG_HOME`, `XDG_DATA_DIRS` (fish reads its configuration from them) and `LUA_INIT`, `LUA_PATH` and `LUA_CPATH` in any version, and those of the other interpreters EnvCloak classes (`R_PROFILE`, `R_LIBS`, `JULIA_LOAD_PATH`, `ERL_LIBS`, `TCLLIBPATH`, `RAKULIB`, `GUILE_LOAD_PATH`, `PLTCOLLECTS`, `PSModulePath`, `AWKPATH`, `MAKEFILES` and their kin) (each changes what code holds the key; a SPEC §6.6 follow-up records them). So are the variables that name a native library or plug-in a program loads by its own choice: OpenSSL's `OPENSSL_CONF`, `OPENSSL_ENGINES` and `OPENSSL_MODULES` (a configuration can name an engine to load), and the GIO, Qt, GStreamer and GTK module paths (`GIO_MODULE_DIR`, `GIO_EXTRA_MODULES`, `QT_PLUGIN_PATH`, `GST_PLUGIN_PATH`, `GST_PLUGIN_SYSTEM_PATH`, `GTK_PATH`, `GTK_MODULES`). An interpreter option counts anywhere in a cluster of short options (`sh -ec`, `perl -we`, `python3 -Bc`), and so do an interpreter's other ways of taking code from elsewhere (`-i`, `sh -s`, `perl -d:Mod`, `php -d`, `lua -l`, `-L` for any of them, `julia -J`, `racket -t`, `elixir -S`, `swift -F`, `node -C`, `--env-file`, `--config`, node's `--snapshot-blob`, `--build-snapshot`, `--openssl-config`, `--run` and `--test`), and a Node package runner's `--node-options`. A long option with `=value` registers only when it is known to load nothing (`--max-old-space-size=`, `--title=`, `--encoding=`, deno's `--allow-*=` and `--deny-*=`, and the few others of `VALUE_LONG`): any other is refused `interpreter_option`, because which options of which interpreter read a file of code is not a list EnvCloak can keep complete. An option before the entry file that may take the next argument as its value (`python3 -X v`, a long option without `=` that is not known to take none, such as `node --title v`) leaves the entry file unknown: reason `no_entry_file`; an attached value registers only when its meaning is allowed. A shell's `-o` and `-O` leave it unknown attached or not: bash and dash take the next argument as the option's name whatever follows in the cluster (`bash -oposix /s.sh` reads `/s.sh` as the name). Ruby's `-W` and `-K` read a short value (one digit, `:category`, one encoding letter) and then read the rest of the cluster as more options, so the letters after the value are checked like any others (`ruby -We'code'` and `ruby -KUe'code'` are refused `interpreter_option`; `-W2`, `-W:no-deprecated` and `-KU` register); ruby's `-T` is refused. Python `-X` allows only `dev` and `utf8` (also `utf8=0` and `utf8=1`), and `-W` only the bare actions `default`, `error`, `ignore`, `always`, `module` and `once`. Other values can import code before the entry script, including debug Python's `presite` and dotted warning categories. PHP's `-f`, `-F`, `-B`, `-R`, `-S` and `-a` forms are refused, including attached values and clusters; register the absolute entry script as a positional argument instead. So is a program that starts another one its arguments name (`env`, `nice`, `nohup`, `stdbuf`, `timeout`, `sudo` and the rest of `envcloak_policy::managed::WRAPPERS`, GNU's with the `g` Homebrew installs them under, `gtimeout`, `genv`, `gnice`, `gxargs` and their kin, and a dynamic loader run as a program), reason `wrapper_program`, and a link named as a program whose file is an interpreter, a package runner or a wrapper (a link `server` to `node`), reason `disguised_launcher`. `migrate-mcp` reports the server as manual. A key-shaped argument, variable value, working directory or `PATH` (or a bridged server's origin or header name) is refused by the client before any daemon contact (gate 13): `envcloak_client::managed::register`, `plan_update` and `update` check the declaration and only then connect, and `migrate-mcp` calls these. A secret a host config held there becomes a binding of the managed manifest, never part of the launch. The daemon refuses one too (`invalid_params`, reason `key_shaped`, audited), in `managed.register`, `managed.update_plan` and `managed.update`, whatever client sent it.

A record created under an older launch policy is checked against the current policy before any request becomes pending or uses a grant. EnvCloak checks both the original declaration and the prepared arguments and environment, including the stored class, entry file and strength. A record that no longer qualifies is refused `managed_launch_changed`; review and update it with a proof to create a new revision. This check preserves the recorded executable and entry: it does not search `PATH` or read the shebang again.

## Launch classes and strength

| Class | What it is | Strength |
|---|---|---|
| `native` | an ELF or Mach-O executable | `bound` on Linux unless its run path names `$ORIGIN`; `bound` on macOS when it has a code directory; `checked_at_rest` otherwise |
| `script` | an interpreter with an absolute entry file (`node /abs/server.js`; an interpreter is matched by its name with any version, `python3.12`, `node22`, `ruby3.2`, `perl5.34`, and CPython's ABI flags and Debian's debug suffix after it, `python3.14t`, `python3.13d`, `python3.7m`, `python3.12-dbg`; architecture suffixes such as `-intel64`, `-arm64`, `-universal2` and `-x86_64`, `pythonw` with or without a version, `graalpy`, `micropython`, `truffleruby` and PHP CGI/FPM names also count; a version starting with a digit keeps interpreter policy even with an unfamiliar build suffix; besides SPEC's list, `Rscript`, `julia`, `tclsh`, `wish`, `pwsh`, `raku`, `guile`, `racket`, `elixir`, `escript`, `osascript`, `swift` and `luajit`), or a `#!` file | `checked_at_rest` |
| `package_runner` | a launcher whose code is chosen when it starts, in any form: `npx`, `pnpx`, `bunx`, `uvx`, `pnpm` and `yarn` (`dlx`, `exec`), `npm` (`exec`, `start`, `run`), `bun x`, `deno task`, `uv` (`run` in any form, `uv --directory <d> run x.py` included, and `uv tool run`), `pipx run`, `poetry run` and the other project runners, `docker run`, `podman run`, `java -jar`, `go run`, `cargo run`, `dotnet run`; and the programs whose arguments name the code they run in a way EnvCloak does not read: `awk` and its kin, `make`, `erl`, `R` | `checked_at_rest` |

**What runs is what was checked.** Every path a launch runs is the canonical one the daemon identified: an entry file named through a link is run by the file's own path, so a link pointed elsewhere later changes nothing that runs. A `#!` file is never handed to the kernel, which would read its line again and, for `#!/usr/bin/env NAME`, look `NAME` up again on the server's `PATH`: the daemon reads the line once, at registration (an absolute interpreter and at most one option, or `env NAME` with `NAME` found on the declared `PATH`), checks the option as that interpreter's own (`#!/bin/sh -c` is refused `interpreter_option`), and the launch runs the checked interpreter explicitly with the line's option, the file's canonical path and the declared arguments. A package runner that is a `#!` file (`npx` is a Node script) runs the same way, its interpreter the executable checked and the runner script its entry file. An interpreter that is itself a `#!` file (a version manager's shim) is refused at registration: it would choose its own interpreter when it starts. A native program given a file is `checked_at_rest`: the file may hold code it runs, which nothing binds. Looked at are each argument, an `--option=value`'s or `-o=value`'s value, a value glued to a short option (`-c/srv/x.conf`) and each declared variable's value: one holding a `/` or starting with `~` counts whether or not the file exists yet (one created after registration loads all the same), and any other that names an entry of the working directory now, of any type, counts too.

**`bound`**: the program that runs is the checked image. On Linux the daemon copies the executable, through the descriptor it checked, into a memory file sealed against writing, growing and shrinking (`memfd_create`, `F_SEAL_WRITE | F_SEAL_GROW | F_SEAL_SHRINK | F_SEAL_SEAL`, the seals checked), hashes the sealed copy and compares that digest with the record, and the runner executes that same copy (`execveat(fd, "", AT_EMPTY_PATH)`): a file rewritten in place or replaced after the check never runs. A run path naming `$ORIGIN` would resolve against the memory file, so such a file is `checked_at_rest`. On macOS the runner starts the registered path suspended (`POSIX_SPAWN_START_SUSPENDED`) and reports its pid; the daemon reads the code directory hash, signing identifier and Team ID the kernel validated the suspended process against and lets it run only when each is the record's (a Team ID of none, ad hoc or platform signed, matches only none; a file whose code directory carries no signing identifier is identified by its SHA-256 and is `checked_at_rest`), otherwise the runner kills it through its handle before it runs and exits `managed_launch_changed`. A timed-out or broken confirmation channel closes the control connection to trigger the runner's cleanup of its own server, and the request returns `runner_unavailable`. The daemon waits up to one second for the runner to exit, then hands a slow runner to a reaper thread: a client that blocks its diagnostic output cannot keep the request open indefinitely. The daemon never kills a runner that may already own that server in another process group.

**`checked_at_rest`**: checked before launch, not bound through the start. On Linux the runner executes the descriptor the daemon checked once its stamp (device, inode, size, change times) is read again and found the same; a `#!` file's interpreter is that descriptor, and the file is its entry. The receipt says what is not bound. Standing approvals (task M2-15) are for `bound` launches only, so such a launch gets once and session approvals.

**Every receipt says** that the guarantee covers the server's main executable only: not its dynamic loader, the shared libraries it loads or anything they load. A `script` receipt says EnvCloak checks the interpreter and the entry script, not the modules it loads; a `package_runner` receipt says the code that runs is chosen by the runner at launch, and how to pin it (install the package and register its entry file). Every receipt carries D-05's sentence: only this server's exact command can receive its key, but any program the agent runs can start that command and read the key from its environment.

## The check before release

For every request against a managed project, the daemon checks, before any pending request exists: the request names the record's launch (or bridge) and carries its descriptors (`managed_command_mismatch` otherwise); the executable's device, inode and identity; a script's entry file; the working directory's device and inode (`managed_launch_changed`, audited `managed_launch` with the part that changed and the old and new device, inode and digest prefix, never a value); on Linux, the sealed copy (`runner_unavailable` when the system refuses an executable memory file, `vm.memfd_noexec=2`; nothing falls back to the file). A launch that changed needs `migrate-mcp --update` and a proof; its refusal says so.

## Updates

`managed.update_plan` builds the next revision from the declaration stored in the record (never a host config, which after migration holds only `envcloak mcp-bridge --stdio --launch <id>`) with explicit changes (`argv`, `cwd`, `set_env`, `unset_env`, `path_env`), resolved in the daemon as a registration is, and answers the old and new receipts and the statement's digest (`envcloak-update-statement/1`) to a caller whose proof the daemon would accept; anyone else gets nothing. `managed.update` makes the plan again, refuses `statement_mismatch` when its digest changed, and commits the same launch id at the next revision. Grants made for the old revision cover nothing of the new one.

## The daemon-started runner

The value recipient is a process the daemon starts itself (M2 plan D-36), never the client that asked: a hardened client's executable cannot be read reliably (on Linux a non-dumpable process's `/proc/<pid>/exe` refuses the daemon, `EACCES`), and a client's identity would prove nothing about where a value goes once it has it.

- A covered managed request is answered `started`. The daemon starts EnvCloak's runner, `envcloak run --launch <id>` (a bridged server's relay, `envcloak mcp-bridge --relay`, the same way), as a child that leads a session of its own, with the client's pipe ends as its standard input, output and error, the lifeline, the checked image and working directory as descriptors, and a control channel on which it sends the values and the launch, once, after the delivery's audit entry is on disk.
- **Its image** is the `envcloak` beside `envcloakd`, taken when the daemon starts: on Linux a sealed copy, hashed once sealed and kept for every start, so an `envcloak` rewritten or replaced later leaves the daemon starting the image it took, until it restarts; on macOS the file's code directory hash and signing identifier, which the started process (suspended) must have, with `envcloakd`'s own Team ID (none for an ad hoc build), before it runs. The daemon reads its own signature, as the kernel validated it, when it takes the anchor; one it cannot read, or an anchor signed by another team, leaves no anchor (`runner_unavailable`): a failed read is never taken for an ad hoc build. The identifier compared is the one the anchor file carried when the daemon started, not `envcloakd`'s own: the two executables are signed under identifiers of their own. An image that cannot be taken or started is `runner_unavailable`.
- **A runner the daemon did not start** receives nothing: before it reads anything it checks that its control channel's peer is its parent and that its parent serves the daemon's socket, and otherwise exits 125 `not_started_by_daemon`.
- **The server** is the runner's child, in a process group of its own, with the launch's environment only: `HOME`, `USER`, `LOGNAME`, `LANG`, `LC_*`, `TZ` and `TMPDIR` from the runner's own (which the daemon set from its own fixed list), the recorded `PATH` and variables, and the bindings; a code-selecting variable is dropped wherever it comes from. Its output goes through the runner's redactor to the client. When the client is gone (the lifeline's end of file), its input ends, or the runner is signalled, the runner stops the server's group through its owned handle: SIGTERM, then SIGKILL after 5 seconds. A server that exits on its own has its group stopped the same way before it is reaped, so a descendant it left in the group (holding the key in its environment) does not outlive it; a descendant that moved to a group of its own is out of the runner's reach. Every thread the runner needs is started before the server, so no setup failure leaves a server running unwatched. The runner then drains the server's output through the redactor; the client's going or a signal stops the drain at once, and a write blocked on an output nobody reads is interrupted, so a client that stops reading never holds a runner.

**Consequences.** Managed servers run as descendants of the daemon, outside the host's process tree:

- they outlive a daemon restart: the systemd unit has `KillMode=process` (`envcloak daemon install` rewrites an older unit), and launchd's cleanup of the daemon's job does not reach a process that leads its own session (measured on macOS 26.4: `launchctl kickstart -k` and `bootout` kill the job's process group, not a child that called `setsid`), so the plist needs no `AbandonProcessGroup`. Neither the runner nor the relay gets `PR_SET_PDEATHSIG`. A new daemon holds no handle to them and signals nothing;
- a command a server starts is classed `unknown` (no terminal, no agent in its chain): no terminal grant covers it, and its proofs are refused;
- the unit's `NoNewPrivileges` applies to them;
- macOS privacy-prompt attribution for a daemon-started server is not yet measured. Protected-folder and local-network prompts are tracked as **M2R-88**, due before the M2 release. CI does not show these prompts and cannot close this measurement.

## Measurements behind this

Measured for task M2-27 (and kept as permanent tests in `crates/envcloak-sys/tests/launch.rs` and `crates/envcloak-e2e/tests/managed_{launch,runner}.rs`):

- macOS 26.4 (the pinned runner's major version): `posix_spawn` with `POSIX_SPAWN_START_SUSPENDED | POSIX_SPAWN_SETSID` starts a child that runs nothing until `SIGCONT`; `csops(CS_OPS_CDHASH)` on it, without extra entitlements, gives the code directory hash `codesign -dvvv` prints; a suspended child killed with `SIGKILL` runs nothing; `posix_spawn_file_actions_addfchdir_np` sets its directory.
- Linux 6.12 (a Debian container on Docker Desktop's Linux VM; CI's `ubuntu-latest` runs the same tests), as a non-root user: a `MFD_EXEC` memory file, sealed, executes with `execveat(AT_EMPTY_PATH)` (no `ETXTBSY`); writing, growing, shrinking and a shared writable mapping are refused (`EPERM`); a non-dumpable process's `/proc/<pid>/exe` refuses another process of the same user (`EACCES`) while an ordinary one's is readable.
