# M3-07: native peer identity

Scope: R-M3-15, R-M3-16 (Rust/CLI half), R-M3-41; M3 g1 (Rust directions), g4, and gates 19, 20, 21 and 22. The Swift daemon check and pins equality belong to M3-10. Developer-profile QA A14/A15 belongs to M3-21. App unlock and approval handlers remain reserved for their respective tasks.

## Build and trust boundary

`envcloak-sys/src/peer_code/pins.rs` holds the three signing identifiers and holds a literal `TEAM_ID` set before compilation. A signed build sets that public Team ID in the source file before building both Rust binaries. Source builds omit it and remain unverified, with no app role. A malformed configured pin fails closed. There is no runtime variable or flag to disable an embedded requirement. The founder's actual Q3-01 Team ID remains to be supplied; no machine credentials or production identity were inspected for this task.

`peer_satisfies` uses the complete kernel audit token with Security.framework's dynamic guest lookup and requirement check. It reads both static and dynamic runtime flags and rejects the presence of debugger or runtime exception entitlements, including false-valued ones. API and metadata failures deny. The daemon caches admission only in one accepted connection; `peer_unchanged` compares uid, pid and exec generation before dispatch, and admission rechecks it after the signature work. App evidence is gathered per request, with claims able only to tighten. Agent evidence and cut chains refuse everything except the reserved `app.lock`.

The Rust client checks the daemon before encoding or sending a request, binds the successful check to the peer instance and checks it again before a request and after a response. `Client::identity` describes that connection. The existing CLI status formatter uses it for text and JSON; the daemon does not vouch for itself in its status payload.

## Native harness

Run `scripts/macos/check-peer-code.sh` outside a recognized agent's ancestry. It creates two disposable identities in explicit temporary keychains under the target directory, compiles the certificate fingerprint only under `testing`, builds the current tree and runs both Rust integration targets with `--no-fail-fast --test-threads 3`. Ordinary crate runs report these native targets as ignored with the runner named. CI runs the native runner explicitly.

On this host `codesign` would not select an untrusted fixture identity. The test-only Objective-C signer in `envcloak-sys/tests/fixtures` passes the identity from its explicit keychain directly to Security.framework's signing SPI. This keeps the account's trust settings unchanged. The SPI is used only to generate test artifacts, never linked into Cargo or the product. Real signature checks use the public dynamic APIs. `codesign` and the independent Swift `SecStaticCode` reader inspect the resulting artifacts.

Apple silicon requires a signature on arm64 executables. The genuinely unsigned fixture is x86_64 and runs through Rosetta on arm64. The runner requires this capability and fails if the fixture cannot execute; an OS refusal is not counted as a daemon refusal. Every fixture has a cleared environment and a short isolated HOME/XDG tree. Frame responses are synchronization barriers. Child cleanup uses owned process handles, and no production certificate, keychain or trust setting is selected.

Its existing `test_sign_check_policy.py` suite is retained as a separate policy check. Native fixture properties are read through `scripts/macos/tests/oracles/codesign_facts.swift`, independently of the Rust code, with real signed positive controls and a DYLD constructor control.

No new proc-macro dependency or build script was added to the workspace. The raw signing-information call is confined to envcloak-sys with ownership and SAFETY comments.

The revised gate uses a separately compiled oracle, signed ad hoc with Apple's

evidence, a failed query or child process, changed policy/signatures, or a
constructor result inconsistent with the independent policy fails the gate.

both hardened constructor markers must remain absent. When that policy allows
them, both constructors must actually run before the runtime portion reports
`unsupported_host`, a visible `UNQUALIFIED` warning, and a unittest skip. It is
never a runtime protection pass. Artifact and peer-identity checks still run.
