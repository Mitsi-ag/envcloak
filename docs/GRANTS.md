# EnvCloak: grants and approvals

Status: M1, and from M2 waiting for an approval and finding a request (task M2-03). This file fixes how SPEC §10a "Bounds and display" and §10b are carried out: what the daemon keeps for a request, how a grant is matched, how a person approves one with the passphrase, what the approval statement is, how a waiter learns how its request stands and how a person finds one, and the bounds on prompts, polls and passphrase attempts. The code is in `crates/envcloak-policy/src/{grants,pending,statement,flood,limiter}.rs`, the waiting in `crates/envcloak-ipc/src/wait.rs`, the daemon handlers in `crates/envcloak-daemon/src/requests.rs`, and the commands in `crates/envcloak-cli/src/cmd/{run,pending,approve,grants}.rs`. The wire form of each method is in docs/IPC.md; the caller evidence a grant is scoped to is in docs/AGENTS.md.

## A request

`envcloak run [--profile NAME] [--ref NAME=slug[#field]]... [--env-file FILE] [--manifest PATH] [--wait DURATION [--wait-grace DURATION]] -- <cmd...>` sends `run.request` with the manifest's path (the nearest `envcloak.toml` upward, or the absolute path `--manifest` names), the profile, the `--ref` bindings, the `--env-file`'s references and the names of its ordinary variables (never their values: those stay with the CLI, whose runner sets them for the command; docs/MANIFEST.md "Env files"), the command line as display text, and the names of the agent markers in its environment. The daemon then, in order:

1. reads the caller's evidence from the kernel (docs/AGENTS.md): the chain, the root instance, the kind;
2. opens the manifest itself from the path sent (a symlinked manifest is refused, SPEC §5) and resolves the bindings from the file it read, the profile, the `--ref` bindings and the env file's references and names (docs/MANIFEST.md "Resolving a run's bindings"); the caller's argv is never used for anything but display;
3. binds each reference to a field of a secret item in the vault, and looks up whether the vault has a record of the project ("new project") and whether any adopted project's bindings name each item ("first use", SPEC §6.4 "Adoption");
4. applies the effective policy: the vault's policy for the project (approve, redact, inject in M1), tightened by the manifest's `[policy]`, for the subject's kind. `agents = "deny"` refuses an agent or unknown subject (`policy_denied`); a required proxy mode is refused in M1 (`mode_unsupported`), never injected;
5. asks the grant store for the decision: `covered` (with the grant id, whether output is redacted, the mode, and whether the manifest's hash differs from the one at approval), `pending` (with the request id) or `denied` (with the reason). A request over a pending cap opens nothing and is not denied: it is answered `too_many_pending` (below, "Bounds").

A covered request is a delivery: its answer carries the bindings' values, and `envcloak run` starts the command with them (docs/RUN.md). An answer those values would make larger than one frame (1 MiB) is refused `frame_too_large` before anything is committed: no value is released, the refusal is audited (`request decision=frame_too_large` with the grant), and the grant is left as it was, so a `once` grant still covers a request for fewer or smaller values (F-77). The values are read and the answer framed after the decision, so the daemon asks again, on clocks read once the answer is built and before anything is committed, whether the grant is in force: a grant that ran out meanwhile, by either deadline, or whose root process exited meanwhile (its pid no longer has the start time the grant recorded; a grant never outlives its root, SPEC §10b), covers nothing. The grant whose root exited is removed then, as the tick's sweep would remove it, and the request is decided again on those clocks, as one arriving then (F-77). A pending run exits 125 with `approval_required request=<id>: run "envcloak approve <id>" in a terminal you control`, or, with `--wait`, prints that line once and waits for the approval (below, "Waiting and finding a request"); either way it reads nothing from its own terminal: that terminal may be an agent's, and a `y` typed there approves nothing.

No decision is made, no statement shown and no proof taken from a vault that failed its integrity check (`vault_tampered`): its project index and policy cannot be trusted. `pending.get` and `approve` are refused so before any key derivation, including for a request that was pending when a read met the change.

## The grant store

The store lives in the daemon's memory under its state lock, is cleared at every lock, and is never written to disk or synced. It holds at most 256 grants and 20 pending requests.

A grant records what SPEC §10b lists: the root process instance (pid and start time, plus the executable for display), the subject's kind and the agent's name, the project identity (canonical directory, device, inode), the manifest's hash at approval, the bindings as (variable, item id, field id) with the display slug and the `live` tick, the mode, `once` or `session`, both deadlines, and the vault and policy epochs.

**Match.** Request R is covered by grant G when all of these hold:

1. G has not passed either deadline (below), been revoked or been used up;
2. G was made under the vault's current epoch and the current policy epoch;
3. G's root is in R's kernel-verified chain, pid and start time alike, and no known agent sits between the root and the caller unless the root is that agent; a grant approved for a terminal subject covers only a terminal subject (docs/AGENTS.md "Coverage");
4. R's project identity equals G's: a symlinked path to the same directory keeps it, a copy (another inode) or a move (another canonical path) is another project;
5. R's bindings are a subset of G's, compared by (variable, item id, field id): a renamed or retargeted variable, an added reference, another field or a profile switch each prompt again, for the difference (below);
6. R's mode is at least as strict as G's.

A manifest change that leaves the bindings a subset does not prompt; the daemon audits `manifest changed grant=<id> approved_sha256=<hex> sha256=<hex>`, the SHA-256 of the manifest's bytes at approval and now, and the decision says `manifest_changed`. A request that is not covered only because of some of its bindings prompts for the difference (SPEC §10b): each binding a session grant in force for the same caller, project and mode already holds is marked `granted` in the pending request, and the statement asks for the others first and lists these apart, under a line saying the new grant holds them too. The new grant holds the whole request, for its own uses and length, so its statement still shows every binding. A `once` grant marks nothing, since it ends at its next use; and the marks are taken when the request opens, so the line says the bindings were covered when the request was made. When a session grant and a once grant both cover a request, the session grant is used and the once grant kept.

**Once.** A `once` grant is used up by the first request it covers. The decision and the consumption happen under one lock, so of concurrent requests exactly one is covered; the others are pending, and identical ones share one pending request.

**Audit before release.** A covered request's audit entry is flushed to disk before the answer, and the values go into the answer only after that (docs/RUN.md "Release"); a `once` grant is consumed only after that too. When the entry cannot be written, the request is denied with `audit_failed`, nothing is released, and the grant is left as it was (VAULT.md "Audit log").

**Deadlines.** An approval sets two: the wall clock plus the grant's length, and time awake plus the same length. Either passing ends the grant, so a clock stepped either way cannot lengthen one. Lengths: 8 hours by default (`--for` sets it, from 30 seconds), at most 24 hours for an agent subject whose root is a known agent process (the agent nearest the caller, SPEC §10b "Root selection"), and 12 hours for every other subject: a terminal or unknown subject, whose evidence is missing, and an agent subject by its claims alone (markers such as `CLAUDECODE=1` set in a person's shell), or by an agent matched only on what it says about itself above the caller's session, whose root is a session's process like a terminal's. Claims only label and tighten.

**A grant ends on** expiry; its first use, if `once`; the root process exiting (a tick every second drops grants whose root's pid is gone or has another start time); `envcloak grants revoke <id> | --all`, which any client may run (tightening needs no proof); lock, for any reason (a request, idle time, sleep, a signal, a restore), which also drops every pending request; a daemon restart, which starts empty; a policy epoch bump; a vault epoch change; the removal of an item it binds (`envcloak rm`), which also drops every pending request that asks for the item. Rotating a bound item's value does not end a grant, unless the new value is classified otherwise: a rotation takes the classification the registry gives the new value (as `items.add` does, for an item of one field), in the same transaction as the value, and a reclassification (test to live, say) ends every grant and pending request that binds the item, since they were approved, or shown, for the old one.

## Pending requests and approval

A request no grant covers becomes a pending request: an id of 8 Crockford base32 characters (unique among the pending requests; `I`, `L` and `O` read as `1` and `0`), a 32-byte daemon nonce, the request as the daemon built it, and the descriptor an approval surface shows (`pending.get`). A pending request expires after 10 minutes of awake time. An identical request (the same root, project, bindings, mode and argv) while one is pending gets the same id.

`envcloak approve <REQUEST> [--once | --for DURATION] [--live NAME]... [--passphrase-fd N]`, run by a person in a terminal they control:

1. refuses under a tracer (gate 19), before anything is read, and refuses (`proof_refused`) when its environment holds an agent's markers;
2. fetches the descriptor, which the daemon serves only to a caller that may give a proof (below), so where none is taken it stops here, before anything is shown or read; and renders the statement (below);
3. reads the vault passphrase from `/dev/tty` with echo off, or from the descriptor named, never from argv or the environment;
4. sends `approve` with the request id, the options, the SHA-256 of the canonical statement it rendered with those options, the passphrase, and the names of the agent markers in its environment.

The daemon, before any key derivation: reads the approver's evidence and refuses every caller but a terminal subject: one with a known agent in its ancestry or agent markers in its claims, a chain cut at the walk's limit, a lost ancestry (an orphan), or no controlling terminal (a service manager's job, a process that forked out and called `setsid`) (`proof_refused`, audited as `proof refused method=<name> reason=<agent|chain_cut|orphaned|no_terminal>`; docs/AGENTS.md "Proofs"); for a request from an agent or an unknown process, refuses an approver that shares a session or a controlling terminal (the same device) with the requester's chain from its caller up to its root, or up to its nearest known agent when that is further (an agent matched only on what it says about itself, or through an extension, roots grants below itself but runs on its own terminal) (`proof_refused` with the reason `requester_terminal`, audited so): approval input is never read from the requester's terminal, where a shell the agent left, or one that took the terminal's foreground, could read or type it (a person approves their own terminal's request there, and an agent's from another terminal window); `pending.get` is refused the same way, so `envcloak approve` stops before it shows the statement or reads the passphrase; checks that the request exists (`no_such_request`), that the options are within bounds (`invalid_options`), that the digest equals the digest of its own descriptor with the same options (`statement_mismatch`), and that the attempt limiter admits the attempt (`too_many_attempts`). Only then does it run Argon2id, with the vault taken out of its slot as an unlock takes it: other requests see `busy` for that moment, and a lock that arrives meanwhile wins. A wrong passphrase gives `wrong_passphrase` and counts. The right one creates the grant and removes the request.

The statement shown by the CLI is advisory: the daemon approves what its own pending request says, and refuses when the digest differs. The passphrase is the proof; a `y` typed anywhere is nothing. `envcloak deny <REQUEST>` refuses a request and needs no proof.

`unlock` is a proof too: it is refused from the same callers as `approve`, and counted by the same limiter. The CLI sends its marker names with it, and refuses before it reads the passphrase when it has any.

A passphrase an agent captured is not made useless by this: a program running as the user can open a pseudo-terminal of its own outside the agent's tree, where it is a terminal subject, and the passphrase opens a copy of the vault file anyway (SPEC §10b "Honest limits"). What the rule gives is that an agent gets no approval, and shows no prompt, from its own tree or from a process without a terminal.

## Waiting and finding a request

SPEC §6.1 step 4 and M2 plan D-04. No client waits for a person on an open connection (docs/IPC.md "Framing"); a waiter asks.

**`pending.state`** answers at once how a request stands: `pending`; `approved`, `denied` or `expired` once it ended, for as long as its outcome is remembered (10 minutes of awake time, as long as a request may wait; at most 256 outcomes, the oldest forgotten first); or `unknown`. It is told only to a caller whose kernel-verified chain holds the request's root instance (pid and start time; a recycled pid is not the root): the requester, and anything else in its root's tree, such as another command of the same agent. Any other caller is told `unknown`, exactly as for an id no request has, so it learns nothing about another tree's requests. A request that left the store some other way (a lock, a daemon restart, an item removed or reclassified) is `unknown` too; the waiter then asks `run.request` again, which says the vault is locked, or opens the request anew. Forgetting an outcome early is safe for the same reason: asked again, a grant covers the request, or a denial remembered for 10 minutes denies it (`repeated`), or an expired request opens anew. `pending.state` opens no request, approves nothing, writes no audit entry, and is not activity.

**The poll limit.** Each subject root has a token bucket for its polls: it refills 4 a second for each of the root's live pending requests (at most 3, so at most 12 a second) and holds one second's worth; a root with none still has one request's worth, to read its outcome. Every poll counts against the caller's own root first, whatever id it names, so a poll refused `busy` says nothing about the id, and one root's polls never spend another's. The daemon reads a poll's time under the store's lock, and a bucket's clock never moves back, so polls that arrive together never refill one interval twice; it refills for every nanosecond its clock moves, so polls however close together lose no refill. A waiter answers `busy` by doubling its pause, up to 2 seconds, and never takes it as a refusal. The daemon keeps at most 1,024 roots' buckets at once; one left alone for a second is full again and forgotten, and past that a new root is refused `busy` rather than another root's budget forgotten.

**`envcloak run --wait <duration>`** (1 second to 10 minutes, the request's lifetime) prints the `approval_required` line once per request and waits: it asks `run.request`, then `pending.state` on a fresh connection each time, pausing 250 ms for the first second, 500 ms for the next, then 1 second; `busy` (from a poll over the limit, or from `run.request` while Argon2id runs for an unlock or an approval) doubles the pause, up to 2 seconds, and a pause never gets shorter. `approved` asks `run.request` again at once, which the new grant covers; `denied` exits 125 with `approval_denied`; still pending at the deadline (one last poll is made there), or `expired`, it exits 125, its `approval_required` line being the failure. A request over a pending cap is answered `too_many_pending`: the waiter prints that line once and asks again with the busy backoff until a place frees or its wait ends. `unknown` at or after the deadline ends the wait as timed out rather than asking again; only `approved` is still asked again then, once. A call the daemon did not take is asked again with the busy backoff until the deadline, as `busy` is: a connection closed, reset or no longer connected before any answer (the daemon closes one at once when 32 are open, or 8 for one process), and, once the daemon has answered this wait, nothing listening there (a daemon restarting; a listener whose backlog is full on macOS, which refuses the connect). At the deadline such a call ends the wait with its failure (`daemon_unavailable`). Before any answer, nothing listening is the failure at once, as it is without waiting, and a socket or a daemon that fails a check, an answer cut short (its connection ending, reset or timing out once part of it has come) and a malformed answer are never asked again. It holds no connection between two steps, makes none outside its wait (`run --wait` does not connect before it), and reads no terminal or input. The waiting is one piece of code, `envcloak_ipc::wait`, for every waiter M2 plan D-04 names.

The wait is bounded by one limit, the deadline plus a grace for the last poll, made at the deadline, and the request after an approval seen then: 5 seconds (`CALL_GRACE`), or less when the waiter passes less (`wait_for_run_with_grace`). No call is answered later than the limit. Each call is bounded by it as a whole, not each read or write by a timeout of its own (`Client::connect_by`): its connect is given the time left (the socket's timeouts are set to it before each connect attempt, so a listener whose backlog is full cannot hold it on Linux), and the connection is then non-blocking, each write and each read waiting for the socket (`poll`) only for the time then left. A daemon that answers nothing, sends its answer a byte at a time, or reads the request slowly therefore holds a call no longer than the limit (tests with each of those peers over real sockets: `crates/envcloak-ipc/tests/wait.rs`, `crates/envcloak-cli/tests/wait.rs`). No call is made once the limit has passed, and an answer read after it is dropped unused, a covered one's values wiped with it. `envcloak run --wait` then exits 125 with `daemon_unavailable`, saying the daemon did not answer within the wait, and starts nothing. A whole wait therefore lasts at most its duration plus its grace: a waiter that must finish within a host's tool timeout (the MCP server and `mcp-bridge`, M2-06 and M2-18) keeps the two together under that timeout, passing a smaller grace when it must. `envcloak run --wait-grace <n>s` (1 to 5 seconds, with `--wait` only) is that smaller grace on the command line: `run_with_secrets` runs `envcloak run --wait <wait less 1 s> --wait-grace 1s`, so the whole wait ends within the tool's (docs/MCP.md "How long a tool waits"). Before each `run.request`, whose answer may carry values, the waiter also looks again for a tracer attached to it, and stops with `traced` (exit 125) without asking if one is: the check `run` makes before it first contacts the daemon (gate 19) is repeated, since a wait can last minutes.

**`envcloak pending [--json]`** asks `pending.list`, which lists the pending requests the caller may approve, oldest first (by when each was opened, then by id), with id, age, time left, the requester's kind and agent, the project's directory and the slugs of its first 32 bindings with a count of the rest (`more_bindings`), so a person can find a request whose id went to an agent host's log. With at most 20 requests pending, a project path of at most 4096 bytes and an agent name of at most 64, the whole list fits in one frame however many bindings a request has (an env file can name thousands); `envcloak approve` shows every binding in its statement. A caller whose proof the daemon would refuse (an agent by any evidence, agent markers in its claims or environment, a lost or cut ancestry, no controlling terminal) gets an empty list, without being told why; a caller that may give a proof is not shown a request from an agent or an unknown process whose chain, up to its root or nearest agent, shares its session or its terminal (the `requester_terminal` rule of `approve`). The CLI prints one line when the list is empty, the same whatever the reason. Nothing is approved there: `envcloak approve <id>` reads the statement and takes the passphrase.

## The statement

The descriptor (`envcloak_policy::PendingDescriptor`) holds: the request id, the nonce (hex), when the request was opened and its expiry, the subject (kind, the agent's name, the caller's pid, the root's pid, start time and executable path), the project (canonical directory, manifest path, manifest SHA-256, whether it is new), each binding (variable, slug, item id, field id, field name, `test`, `live` or `unknown`, whether it is a first use, whether a grant in force already holds it), the mode, and argv.

**Canonical encoding** (`canonical_statement`): the bytes `envcloak-statement/1\n`, then every field of the descriptor and of the options (`once` or `session`, the length in seconds, the `live` names), each as a 4-byte big-endian length followed by the bytes, lists preceded by their count, numbers as decimal strings (a pid with its sign, so a pid and its negative, which render differently, never encode alike; a positive pid encodes as it always did), booleans as `1` or `0`. Nothing is ambiguous whatever the strings hold, and the full argv is in it. `statement_digest` is its SHA-256. The nonce binds the digest to one request of one daemon.

**Rendering** (`render_statement`): the text a person reads. Every string from the daemon goes through `escape_for_display`: backslash, `\n`, `\r` and `\t` as those escapes, and every other control character, bidirectional control, zero-width or other invisible character as `\u{...}`. The bindings no grant covers come first, under a line saying the request asks for them, and those a session grant already held follow under a line saying this grant holds them too. Argv is a list, one argument per line with its index; rendered argv beyond 2048 bytes is cut on a character boundary with `(N more bytes)` and a line saying that the passphrase approves the full command line. The rendering ends with "The passphrase you enter approves exactly this, and nothing else."

`envcloak grants list` escapes what it prints the same way. Its `--json` form, like every `--json` the CLI prints, is written by one JSON writer that escapes the same characters as `\uXXXX` (C1 controls, DEL, bidirectional controls, zero-width characters, tags), paths included; JSON's own encoding escapes only U+0000 to U+001F, the quote and the backslash.

## Sign-in scope and statement

A dev sign-in (SPEC §6.8) is approved over its own statement, never an inject or proxy one, and only a sign-in authorization whose scope equals the request's field for field covers it (SPEC §10b). The contract is pure code in `crates/envcloak-signin`, which the daemon calls as its only implementation.

**Scope encoding** (`SignInScope::encode`): the bytes `envcloak-signin-scope/1\n`, then fields 1 to 31 in order, each as a 2-byte big-endian field number, a 4-byte big-endian length and the value. Values are typed: integers as fixed-width big-endian (a pid as a 4-byte two's complement number, so a pid and its negative never encode alike), ids and digests as their bytes, text as UTF-8, an optional value as `0` or `1` and the value, enumerations as one byte, and a composite value as its parts each preceded by its 4-byte length. A set is a 4-byte count and its elements, each length-prefixed, in ascending order of the element's bytes; a set given with a duplicate is refused, so the order a caller lists it in never changes the encoding. The fields: 1 the subject root (pid, start time), 2 the SHA-256 of its evidence, 3 to 6 the project's canonical directory bytes, device, inode and the SHA-256 of its effective sign-in configuration, 7 to 12 the login item id, its authorization revision, the expected account, the tenant (optional), the exact role and test (`1`) or live (`2`), 13 to 16 the target id and revision and the adapter id and revision, 17 the credential-entry origins (each: the scheme, `1` http or `2` https; the host, `1` and a name, `4` and an IPv4 address or `6` and an IPv6 address; the port as 2 bytes), 18 the identity check (`1` endpoint or `2` element, and its locator), 19 the declared cookies (each: its name; its domain, `1` and the host for a host-only cookie or `2` and the name for a domain cookie; its path as the browser stored it; its partition, `0` for none or `1`, the top-level site's scheme and host and `1` or `0` for the cross-site ancestor bit), 20 the declared storage keys (each: the origin and a key of its local storage), 21 the delivery mode (`1`, browser session delivery), 22 the requesting process instance, 23 the browser instance's generation, 24 the tier (`1` each, `2` dev), 25 the attempt count, 26 to 28 the approval window, per-attempt timeout and session lifetime in seconds, 29 to 31 the daemon instance, vault epoch and policy epoch. No credential is in it. Its SHA-256 is the lookup fingerprint a retry is found by.

**Statement encoding** (`SignInStatement::canonical`, domain `envcloak-signin-statement/1`): the bytes `envcloak-signin-statement/1\n`, then fields 1 to 7 the same way: the scope's whole encoding, the 16-byte request id, the 32-byte daemon nonce, creation and expiry in Unix seconds, the options (`1` for once; `2`, the window in seconds as 8 bytes and the attempts as 1 byte for dev) and the reserved recipient-context id as 8 bytes. Its SHA-256 is what a proof approves. The nonce and the context are the statement's, not the scope's, so they never change the lookup fingerprint. `crates/envcloak-signin/tests/oracles/signin_encoding.py` encodes both independently and the tests compare byte for byte.

**Operations** (`OperationStore`): looked up by owner root, daemon instance and `operation_key` (1 to 128 of `[A-Za-z0-9._-]`, compared in constant time, never logged). The same key and scope join the operation; the same key with any field changed is `request_conflict` and changes nothing; status, cancel and end from another root answer as for an id that never existed. At most 256 operations per root and 4,096 in all; a full store refuses rather than forgets. A stopped operation's receipt is kept until its `retry_until`, 10 minutes after it stopped, and while its cleanup is unconfirmed: a teardown that is pending or whose close failed keeps it as a tombstone until a later report confirms the close. A new key is covered only by an authorization for exactly its scope: every part of it changed alone, each field and each part of a declared cookie, storage key or origin, needs its own proof. A `once` approval reserves its one credit for the approved operation and lasts the scope's approval duration; a `dev` approval (1 to 5 credits, 3 by default, within a window of at most 24 hours from the approval and at most the approval duration) also covers new keys of exactly its scope while it is in force and has credits. Credits are reserved with the epoch and deadline check in one step and never refunded; nothing extends a deadline. An authorization covers its operations' attempts, their publication and every tool call on a delivered session, which ends with it (its deadline, lock, root exit, an epoch or revision change). Attempts on one login are serialized: an attempt holds its login from its start until it captured or its teardown was confirmed, so a failed close holds it. Every call first brings the store up to date with the clock and the world as they are at that call, so a change that no call has seen yet is seen by the next one, whichever it is. Declared state goes only to the browser supervisor of the attempt's generation, and publication is one decision that re-checks the stop, the generation, the injected state, the exact identity, the root, the epochs, the revisions, the recipient, the attempt deadline and the authorization. Host names are checked by `HostName::new`, the only way to make one, and a last label the URL standard reads as a number (all digits, or `0x` and hex digits) is refused; `crates/envcloak-signin/tests/oracles/host_serialization.mjs` (Node's WHATWG URL parser) checks that every accepted name is one the browser serializes as itself. A declared cookie names what the browser keys a cookie by (its name, host-only or domain, path and partition), and two browser measurements kept as metadata (`tests/oracles/cookie_scope_corpus.json`, `tests/oracles/cookie_partition_observations.json`) check that declarations differ exactly where the browser stored or delivered cookies differently. The gates b7, b8, b9, b14 and b17 are checked at this level by enumerating every ordering of up to 7 events over two operations, from an empty store and from a delivered session, with the world's and the clock's changes made silently so that the next call is the first to see them (`crates/envcloak-signin/tests/enumeration.rs`), and case by case in `tests/store.rs`; M2b-05, M2b-08 and M2b-09 close them against the real daemon, supervisor and worker.

## Bounds

- At most 3 pending requests per root and 20 per daemon. A request beyond either opens nothing and is not denied: it is answered `too_many_pending`, with the reason `pending_per_root` or `pending_total`, and audited so (`request decision=too_many_pending`). Nothing was refused and nothing asked of a person, so a waiter asks again with backoff and a run that does not wait exits 125.
- A waiter held back by a full cap asks again as often as every 2 seconds, so `too_many_pending` is not audited once per answer, which would grow the log with waiting time: for each request (its fingerprint: root, project, bindings, mode and command line) the first answer is written at once with `count=1`, the ones after it are counted for a minute and written together by the daemon's tick as one entry whose `count` is how many answers it stands for (the last of them, stamped when written), and whatever is still counted is written when the vault locks, the daemon's stop included. Each answer is in exactly one entry unless the daemon is killed, and a request crowded out for 10 minutes writes about 11 entries rather than about 300. At most 64 requests are counted at once; past that an answer is written at once, `count=1`, and no count is dropped to make room (`crates/envcloak-daemon/src/crowded.rs`).
- A request identical to one denied in the last 10 minutes is denied without a prompt (`repeated`).
- Three denials for one root within 10 minutes deny that root for 30 minutes (`root_denied`), whatever it asks: the store checks this before it looks for a grant, so a grant the root already holds covers none of its requests meanwhile. The grant is kept (revoke it with `envcloak grants revoke` to end it) and covers again when the 30 minutes end. The daemon logs a notice, until there is a surface for a notification (M3).
- Denials are remembered for their whole 10 minutes, and this state outlives a lock, since it only tightens. None is forgotten early to make room: while 64 are remembered, no new pending request is opened (`denials_full`) until the oldest is 10 minutes old, so a denied request never prompts again inside its window and a root's count toward the auto-deny is never reset. Only a pending request can be denied, so at most 64 plus the 20 pending requests are held.
- The passphrase attempt limiter is one for every proof: after 5 failures, each further attempt must wait, 30 seconds after the fifth failure and twice as long after each failure beyond it, up to an hour; an attempt that comes early is refused without a passphrase being checked. A success clears it. `envcloak status` shows the failures and the wait.
- Windows count time awake: a machine asleep serves none of them.
