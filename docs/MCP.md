# EnvCloak: the MCP server

Status: M2 (task M2-06). This file fixes how `envcloak mcp` carries out SPEC §7's MCP tools: the transport, the session, each tool's input and output, how `run_with_secrets` runs a command, how long a tool waits for a person, and what the server never does. The code is in `crates/envcloak-mcp` (the server and the tools) and `crates/envcloak-cli/src/cmd/mcp.rs` (the command); each host's tool cutoff is in `crates/envcloak-agents/src/tool_timeouts.rs`. Installers (M2-08, docs/INSTALLERS.md) write the host entries that start it, and `run_with_secrets` shares their hook's argv check; the sign-in tools and the hosted browser of M2b plug into its router later.

## What it is

`envcloak mcp [--host ID] [--wait-ms N]` is started by an agent host (Claude Code, Codex, any MCP client) and speaks the Model Context Protocol over its standard input and output. It is EnvCloak's own client binary in another mode, hardened as every command is (core dumps off, non-dumpable on Linux, panics showing their place only), and it is a hand-written JSON-RPC server on `serde_json` (plan decision D-01): no async runtime and no code-generating macro.

It never receives a value. The metadata tools ask the daemon for metadata only, and `run_with_secrets` runs a child `envcloak run`, which alone receives the values from the daemon, starts the command with them and redacts its output before this server reads it (D-03). So "the same policy and redaction path as `envcloak run`" (SPEC §7) is literally `envcloak run`. The server never offers a proof and holds no approval path: the person approves in a terminal of their own (`envcloak pending`, then `envcloak approve`), and approvals from the agent's session are refused by the daemon (SPEC §10b).

## Transport and session

- **Framing.** One JSON-RPC 2.0 message per line, in UTF-8. A line is at most 1 MiB: a longer one is answered with a parse error (`-32700`) as soon as it passes the cap, before its end, and the rest of it is read and dropped without being kept, so a line of any length costs no more memory than the cap. A message cannot hold a newline; one sent with one arrives as two lines, each refused. Invalid UTF-8 and anything that is not one JSON value is a parse error. A batch (a JSON array) is refused (`-32600`): MCP removed batching in 2025-06-18.
- **Ids.** An id is an integer, or a string of at most 64 ASCII letters, digits, `_`, `-`, `.` and `:`, holding at most 23 letters and digits in all (one short of the shortest run a key is taken to be), that is not shaped like a key or token. Any other id is answered as an invalid request with a `null` id, so a key, a URL, a passphrase or a Recovery Kit (28 symbols in groups joined by `-`) sent as an id is never echoed, whatever separates its parts; so is a UUID, a common shape for API keys. MCP clients number their requests, which this takes whole. An id the rule takes is echoed, as JSON-RPC requires; the host chose it, and a plain string of that shape (a token of up to 23 letters and digits) cannot be told from an id. A request whose id is still in hand is refused.
- **No echo.** Every error is a code and fixed text. No method name, tool name, argument, property name or value from the input ever appears in an answer or on standard error.
- **Lifecycle.** `initialize` negotiates the version: a client that asks for `2025-11-25` or `2025-06-18` gets that version, any other gets `2025-11-25` and decides whether to go on. The server declares the `tools` capability only (`listChanged: false`), with its name, version and a short `instructions` text. `ping` is answered at any time. Before `initialize`, `tools/list` and `tools/call` are refused (`-32600`); a second `initialize` is refused. `notifications/initialized` is expected but not waited for. Resources, prompts, logging and the other methods are unknown (`-32601`). `tools/list` is one page; a `cursor` is refused.
- **Standard output** is written by one thread only, one whole message at a time; no child process inherits it. It holds answers and nothing else, also while the daemon is down. Diagnostics go to standard error and are value-free. The answers waiting to be written are bounded, at most 1,024 messages and 8 MiB (one larger message is taken when nothing waits): a host that goes on sending but stops reading the answers fills them, and the session then ends. The server stops reading, stops the calls in hand as at the end of input, and exits 1 with `output_stalled`; it waits at most 5 seconds for a write the host does not read, so it never hangs on one.
- **Calls.** At most 4 tool calls run at once and 32 more wait; a call beyond that is answered at once with `-32008` (`busy`, the error kind EnvCloak's own protocol uses for a full limit, docs/IPC.md). A call's time (the wait below, which keeps it under the host's cutoff) runs from its arrival, the time it waits for a worker included: a call still waiting for a worker when it runs out is answered `busy` then (a tool failure, nothing run), whether or not a worker is free, so calls that hold every worker longer (four approved commands that run for minutes) leave none unanswered past the cutoff; a call the host cancels while it waits leaves the queue at once; `run_with_secrets` is given only what is left of the wait for the person, and refuses the same way when even its shortest run (1 second for the person, 1 for the daemon's last answer) would end more than half a second after a call that never waited; and every daemon call of a tool is bounded by the same deadline. `tools/call` naming a tool that is not listed, whether nothing has that name or a tool is registered but not listed, is answered `-32602` with the same fixed text (M2b-06 relies on it: an unlisted tool cannot be reached by guessing its name); `-32601` is for an unknown method only.
- **Cancellation.** `notifications/cancelled` for a call in hand: the call is answered nothing, ever. One still waiting is dropped. One running has its child stopped: the child's process group gets `SIGTERM`, which `envcloak run` passes on to its command; if the child has not exited within 2 seconds, a second `SIGTERM`, on which `envcloak run` kills its command (`SIGKILL` in place of the second, sent through the handle `envcloak run` owns, docs/RUN.md "A second SIGTERM"); and `SIGKILL` to the child's group if it has still not exited 2 seconds later. Once the child of a stopped call has exited the child's group gets `SIGKILL`, so nothing left in it outlives the call; the server reaps the child only after its output has been read, so a call cancelled after its child exited, while that output is still read, has the group killed at once (there is no `envcloak run` left to pass a `SIGTERM` on). An answer already made but still waiting to be written, behind writes the host has not read, is withdrawn: only one the writer has begun to write still goes out (the cancellation came after it was sent, as MCP allows). Where the command is depends on the session the host started the server in:
  - **With a controlling terminal** (a host that starts its stdio servers in a terminal session of their own, as an interactive host running in a terminal window may; which pinned hosts do is not measured yet, docs/AGENTS.md "Host behaviour"), `envcloak run` keeps its command in its own group, the one the server started: the command and what it started there end with that `SIGKILL`, however soon `envcloak run` exits (a command killed on the second `SIGTERM`, one that died of the first while a descendant ignores it, or one that had exited while `envcloak run` still read what a descendant wrote).
  - **Without one**, the command leads a group of its own, which only `envcloak run` owns: `envcloak run` kills it on the second `SIGTERM`, and, once it got a `SIGTERM`, kills what is left of it before it reaps the command: when the command exits, or, for a `SIGTERM` that came after the command exited while its output was still read (a descendant holding the pipes, up to 2 seconds), when that reading stops (docs/RUN.md "What a SIGTERM leaves behind"). `envcloak run` reaps the command only after its output, so the group is still the command's then.

  So a command that ignores `SIGTERM`, and what it started in its group, end with the call, with a terminal or without, whether the call is cancelled while the command runs or after it exited while its output is read. Each child starts with `SIGTERM`, `SIGINT` and `SIGHUP` unblocked, though the server blocks them in every thread to take them on one: a child that kept that mask could not be stopped by them, and an `envcloak run` still waiting for an approval would start its command once the approval came, after its call was cancelled. `envcloak run --wait` itself makes SIGINT and SIGTERM end the wait however it was started (docs/RUN.md "Waiting"). Cancellation does not deny the pending request: a person can still approve it, and the next call is then covered; the cancelled call's `envcloak run` is gone by then and starts nothing.
- **Shutdown.** At the end of standard input, when standard output closes (a write fails, or the answers waiting for the host fill), or on `SIGTERM`, `SIGINT` or `SIGHUP`, every call still running or waiting for a worker is stopped the same way and waited for, at most 8 seconds; answers already made are left to the writer (at most 5 seconds more); then the server exits (by the signal, for a signal). Standard input is read on a thread of its own, so a closed output ends the session at once, while the host keeps its input open and sends nothing.
- **Signals go only to owned children.** Each child (`envcloak run`, `envcloak check`) is this server's own child and leads a process group of its own; the group is signalled only while its leader is unreaped, under the same lock that marks it reaped before it is reaped, so a signal never reaches a reused process number (plan §6 rule 3, D-34). The `SIGKILL` that ends a stopped call's group is sent under that lock too, after the leader's exit was seen (`waitid` with `WNOWAIT`) and before it is reaped, which is only once its output has been read. Children are started one at a time: on macOS a pipe gets its close-on-exec flag only after it is made, so a child started meanwhile by another worker would inherit another call's pipes, and could hold that call's output open or write into it. That ordering covers the pipes made for a child, not every descriptor the server makes (another worker's connection to the daemon, whose socket on macOS also gets its flag only after it is made, can be made meanwhile and inherited by a child). What a child inherits that way never reaches a command: `envcloak run --status-fd` sets the close-on-exec flag on every descriptor it inherited above the standard streams before it starts anything (docs/RUN.md "Status descriptor"). `envcloak check` starts no command.

## The tools

Each tool has an input schema with `additionalProperties: false`, an output schema, and answers with `structuredContent` and the same JSON as its text. Arguments are checked here against the schema, not trusted to the host: an unknown, missing or mistyped property is refused with `invalid_params` and fixed text. Every string argument shaped like a key or token is refused unechoed (`value_on_argv`, gate 13), before anything is started or asked of the daemon: the message says to name keys by reference and to rotate one that was pasted. A tool's failure is a result with `isError` and the text `{"error": <token>, "message": <fixed text>}`, using the CLI's own tokens (`daemon_unavailable`, `vault_locked`, `invalid_path`, `manifest_invalid`, `no_such_item`, `not_secret`, `run_failed`, ...).

Annotations are hints a host may ignore (D-22): `list_secrets`, `project_status` and `request_new_secret` carry `readOnlyHint`; `run_with_secrets` carries `destructiveHint` and `openWorldHint` and never `readOnlyHint`; `add_reference` is neither read-only nor destructive. No tool carries both a read-only and a destructive hint. Whether each host asks the person before a call is tested against the real hosts, not assumed from the hints. The installer never pre-approves `run_with_secrets` (D-22).

There is no reveal tool and no doctor tool, and `usage_summary` is not listed before M4 (gates 34, 35 and 36).

- **`list_secrets { project_dir? }`.** The vault's items: slug, class, provider, test or live, field names, and `exposed`: true for a key marked "exposed: rotate" (its value was found outside the vault, in an agent transcript, git history, a config backup, a synced folder, a shell profile, an agent config or an env file; `items.mark_exposed`, M2-11, sets it, and a rotation that leaves the item holding no value the mark covers clears it), false for any other key. An item that is not a secret is shown by slug and class only, with `exposed` null. With `project_dir`, its `envcloak.toml` (there or above) and each binding's variable, reference and whether it resolves. Names the daemon sent are shown escaped, and one shaped like a key is replaced by a placeholder.
- **`project_status { project_dir }`.** The manifest, each binding and whether it resolves, and the env files' plaintext keys by count, from a child `envcloak check --json` run in `project_dir` (so the env files are read by the CLI's own reader, never by this server), read whole when it is up to 128 KiB (a longer report, of which bytes were left out, is `run_failed`); the vault's state; the requests this server's `run_with_secrets` calls left waiting for approval, as they stand now (an agent is never shown the person's list of pending requests, SPEC §10b; at most 32 are remembered, and `pending_untracked` says when one was not); the grants that may cover this server's `run_with_secrets` calls, each by its id as `envcloak grants list` shows it: SPEC §10b "Match" rules 3 and 4 as the daemon applies them (`SubjectEvidence::covered_by`), to this server's own evidence, which it reads as the daemon reads a caller's (`envcloak_policy::gather`: its ancestry from the kernel, the agent catalog the daemon loads, the agent markers in its environment), since the daemon does not tell a client the evidence it read; so a grant rooted above the agent (a terminal grant of the shell that started it) is not shown, nor a terminal grant to an agent; `coverage`, which is `null` in this build (`envcloak agents status` has not shipped, so no surface is reported active); and the features that are unavailable, each with the milestone that brings it (`paste_sheet` M3, `usage_summary` M4, `proxy_mode` M6; reveal and doctor never over MCP). The whole call ends within the wait: the check and every daemon call share one deadline, the daemon asked on one connection bounded by it, and a call that would pass it fails (`run_failed` for the check, `daemon_unavailable` for the daemon).
- **`add_reference { project_dir, env_name, slug, profile? }`.** Binds a variable to an item in the project's `envcloak.toml`, as `envcloak ref` does: everything else in the file is kept and the file is replaced atomically (`envcloak_client::manifest_edit`). The daemon is asked what the slug names first: a slug no item has (`no_such_item`), a login (`login_reference`: its fields are typed, and only a sign-in opens them) and any other item that is not a secret (`not_secret`) are refused before the file is touched. The binding is a request, not an approval: the next run that uses it asks the person.
- **`run_with_secrets { project_dir, argv, profile? }`.** Refuses, before the daemon is asked, an `argv` that EnvCloak's `PreToolUse` hook would deny in the agent's shell (D-22, M2-08): one that reads an env file, prints the environment, runs `envcloak reveal` or `envcloak approve`, whose commands cannot be told (`sh -c` of a script the check cannot read), or whose reads it cannot resolve (the hook's `unresolved`, which it asks the person about in Claude Code; the server has no one to ask), with the token `command_refused` and the hook's own message (`envcloak_agents::hook::decide_argv`, docs/INSTALLERS.md), so a host without hooks gets the same accident prevention. Otherwise it runs `argv` (1 to 256 arguments, at most 128 KiB in all, no shell) through `<this envcloak> run --status-fd <fd> --wait <n>s --wait-grace 1s [--profile p] -- argv` in `project_dir`, with standard input from `/dev/null` (a command that reads it gets end of file at once) and its output on pipes. How the run ended comes only from the status record `envcloak run` writes on `<fd>`, the write end of a pipe of this server's that the command never holds (docs/RUN.md "Status descriptor"), never from the exit code or the output: a command can exit 125 after printing `envcloak: approval_required: ...`, and it ran all the same (Codex F-113). The result:
  - `approval_required`: the request named, and the message "Request <id> needs the person's approval in EnvCloak. Ask them to run `envcloak pending` and approve it from a terminal of their own; approvals from this session are refused." with the time waited, that the call can be made again once it is approved, and that the command then runs outside the host's sandbox and holds the injected keys while it runs. When the daemon proposed test items for live bindings (SPEC §10b "Live-key guard"), the message names each, from the run's status record: the variable, the live item, the test item and how to bind it in the live one's place for the layer the binding came from (`envcloak ref NAME=...`, with `--profile` for a profile; `add_reference` does the same), and how many more were proposed than the record names (at most 8); a name of one that looks like a key or token is not shown. `envcloak run`'s own line, which names `envcloak approve`, is not passed on: nothing invites the agent to approve (T-15);
  - `denied` or `refused`: when the record says `envcloak run` stopped before it started the command, its token, its exit code and its own message for that token (a vault locked, a binding unresolved, the daemon down, a value too short, a command not found); nothing else wrote to its output then;
  - `execution_unknown`: no record, or one cut short, doubled, too long, written other than its one encoding or otherwise malformed, or one saying the runner failed after the command may have started: the command may have run, with the output as far as it came; never taken as not run, so the agent is not invited to run it again blindly;
  - `completed`: the record says the command ran: its exit code (with the signal, when one ended it or stopped the run, and the exit code a shell gives for that, 128 plus the signal) and its standard output and standard error, redacted by `envcloak run`, whatever they hold, `envcloak:` lines included; only the record's request id is ever tracked for `project_status`. Each stream is kept as its first 64 KiB and its last 64 KiB, with the marker `[envcloak: <n> bytes of output left out here]` between them. A word cut by the head's end or the tail's start (a run of bytes that could be part of a key) is dropped whole, however long, and counted with what was left out: what is left of a key past a cut has no prefix for a pattern to match, so no piece of one is shown. Output still open 2 seconds after the command exited (a descendant holding it) is not read further; its last word is dropped the same way, and the marker `[envcloak: the output was not read past here]` ends it (`output_cut`). Every word a provider's key pattern matches is masked here too (`Registry::mask_keys`), for keys the run does not bind.

  The tool's description says that each key and its common encodings are masked in the command's output while output the command transforms (part of a key, a re-encoding, compression or encryption) is not, that the command runs outside the host's sandbox and holds the injected keys in its environment and memory while it runs, and that what it does with them is up to the command (R-M2-02, R-M2-03, SPEC §1.1 "Inject + redact" and §6.1). The server's `instructions` say the same of masking, and that no tool returns a key's value; tests hold both texts to it (`tools_list.rs`, `lifecycle.rs`).
- **`request_new_secret { provider }`.** Takes the provider's name, never a key, and returns the terminal instruction: ask the person to run `envcloak add <provider>` in a terminal of their own and enter the key at its hidden prompt; never ask them to paste a key into the conversation (D-20). A provider the registry does not know is not echoed: the instruction is then `envcloak add`, which tells the provider from the key's shape. From M3 the app's paste sheet takes its place.

## How long a tool waits

A tool that waits for a person answers before the host gives up on the call. `--wait-ms` (1,000 to 20,000) sets the wait; without it the wait comes from `--host`: the host's MCP tool cutoff as the installer sets it, less 2 seconds, from 1 to 20 seconds. The wait holds the daemon's last answer too: `run_with_secrets` gives `envcloak run` the wait less 1 second for the person (`--wait`, whole seconds, rounded down, at least 1) and that second for the daemon's last answer (`--wait-grace 1s`, where `envcloak run` alone would give 5), so a daemon slow to answer at the deadline cannot push the answer past the wait; the 2-second margin is left for starting and ending the processes (`envcloak_agents::tool_timeouts::person_wait`).

| `--host` | Cutoff, as the installer sets it | Default wait |
|---|---|---|
| `claude-code` | the per-server `timeout` in its MCP entry, 60 s (Claude Code 2.1.280 cut a 70 s call off at 60.0 s under `"timeout": 60000`; docs/AGENTS.md "Host behaviour") | 20 s |
| `codex` | `tool_timeout_sec`, 60 s (Codex 0.159.2 cut a 15 s call off at 5.0 s under `tool_timeout_sec = 5`) | 20 s |
| any other, or none | 10 s, the cutoff SI-17 measured for Claude Code without a per-server timeout (K-08) | 8 s |

Measured end to end (crates/envcloak-cli/tests/mcp.rs): with a request left pending, each default answers with it after waiting for the person and before its cutoff (an unknown host's after about 7 s); with a daemon that stops answering once the request is pending, each default still answers before its cutoff (an unknown host's after about 8 s); under the pinned Claude Code with the installer's 60 s timeout, S8's first answer reaches the model after about 19 s (crates/envcloak-e2e/tests/m2_story/mcp.rs).

## Limits

- **A process that leaves the command's group.** Cancellation ends the command's process group, with a terminal or without (a command that ignores `SIGTERM` included, and what it left in its group). A process the command started in a new session or group of its own (a daemon it spawns) is outside that group and is not signalled: EnvCloak signals only groups it owns (plan §6 rule 3, D-34). It keeps whatever values it was given.
- **An `envcloak run` that does not answer.** Without a terminal, the command's group is ended by `envcloak run`, which owns it; were `envcloak run` itself stuck past both `SIGTERM`s, the server's last `SIGKILL` would end `envcloak run` alone, and the command's group would be left.
- **A call that ends by itself.** What a command leaves running when it exits on its own (a background process holding the values) is not stopped: only a stopped call's group is killed. Its output is read for 2 seconds after the command exits, then cut; a call cancelled in those 2 seconds is stopped, and what the command left in its group goes with it (above). A cancellation that comes once the output has been read and the call is ending is too late: the call is done, and what the command left runs on, as it would have.
- **The shortest waits.** With `--wait-ms` under 2,000 the person still gets 1 second and the daemon's last answer 1 more, so the answer can come up to 1 second after the wait, within the 2-second margin.
- **Commands the hook misses.** `run_with_secrets` refuses only what EnvCloak's hook would deny in the agent's shell; the commands that hook lets through (docs/INSTALLERS.md, "What the hook does not see": a script an interpreter runs, a copy of the file, a program not on its reader list) run, with their output redacted as every command's is.
- **Outside the host's sandbox.** MCP servers run outside the host's sandbox (Claude Code's sandbox applies to its shell tools; Codex's network proxy does not filter MCP servers), so `run_with_secrets` does too, and holds the keys while it runs (§1.1). The host's own approval of the tool is the remaining check on it, which is why the installer never pre-approves it.
- **Key-shaped arguments.** A run of 24 or more letters and digits that mixes cases or digits counts as shaped like a key, so an argument such as a commit hash is refused too; run such a command with `envcloak run` in the agent's shell.
